# 让数据自己诊断：GPTOPS 的 DGX Spark 黑客松十日谈

> 第三届 NVIDIA DGX Spark Hackathon · 团队 GPTOPS · 作品 SparkDBA
> 代码：https://github.com/GPTOPSGPT/SparkDBA
> 团队成员：张成宇（队长）、史钱龙、齐冬娜

## 一、选题：先想清楚「怎么证明它有用」

9 月 20 日训练营结束、实验云节点开放之后，我们手上有三个候选方向：品牌内容智能体 BrandMind、TiDB 上的数据洞察 Insight，以及我们一直在做的金仓（KingbaseES）数据库诊断项目。

最后决定方向的，是训练营里讲的 NVIDIA 技能验证方法：同一个智能体，加载技能和不加载技能各跑一遍，在安全、正确、可发现、有效、效率五个维度上比较，而且必须有负向用例。这套方法最怕的是「好不好全凭感觉」。数据库诊断恰好有**客观的标准答案**：实验室注入的是什么故障，答案就是什么。技能带来的提升可以是一个数字，而不是一段描述。

另一个理由是本地运行。SQL、会话、设备遥测都是企业资产，不能发到云端大模型。「模型、数据库、评测全在一台 DGX Spark 上」本身就是这个场景需要的形态。

于是有了 SparkDBA：把金仓诊断项目的业务逻辑搬到 PostgreSQL 16，再加一个 TDengine 工厂遥测模块，用我们自己的智能体和 9 个 Agent Skills 来诊断。

## 二、搭起来：一台机器装下所有东西

节点是一台 GB10、121 GB 统一内存的 DGX Spark。我们在上面依次装好：

- **模型**：NVIDIA Nemotron-3.5-Lightning 30B-A3B 的 NVFP4 版本，用 vLLM 本地服务，实测约 77 token/s。30B 的 MoE 只激活 3B，内存里还能同时放下 KV cache 和两个数据库。
- **数据**：PostgreSQL 16 加一个会话采样仓库；TDengine 3.4 里跑一个模拟工厂，3 条产线、15 台设备，每秒一行遥测。
- **故障实验室**：锁竞争、长事务未提交、表膨胀、连接堆积、缺失索引、健康对照 6 种数据库故障，加上过热、轴承磨损、气压不足、设备离线、传感器卡死 5 种设备故障，都能一键注入、一键停止。

金仓自带 KWR、KSH、KDDM，原生 PostgreSQL 没有。我们用 `pg_stat` 视图把三件套重建成 PWR（计数器快照）、PSH（每秒会话历史）和 PDDM（Top-5 阈值判定）。有了会话历史，故障结束之后也能复盘，这正好对应「等人上线，现场已经没了」这个痛点。

编排框架做成可切换的：评测用我们的内置 harness（记录每一步），另外接入了组委会参考的 OpenClaw 和 Hermes Agent。同一套技能在三个框架里都能被发现，说明技能本身是可移植的。

## 三、踩过的坑

这一段最值得记下来，因为每个坑都让系统变得更可靠。

**1. Hermes 报「上下文超长」。** Hermes 默认把 `max_tokens` 设成等于模型的上下文长度，vLLM 直接返回 400。把 `model.max_tokens` 设为 4096 之后恢复正常。教训：接入新框架时先看它默认发出去的请求参数。

**2. OpenClaw 不认软链接。** 我们一开始把技能目录软链接到 OpenClaw 的技能目录，结果一个都没被发现。改成复制，并在安装脚本里自动完成首次引导（onboard）。

**3. 权限只存在于命令历史里。** 我们做了一次「从 README 全新安装」的测试：按文档从干净的代码装到同一台机器的第二个目录。第一次就发现 8 个问题，其中最有价值的是一个线上系统里潜伏的 bug：处置角色从没被授予 `pg_reload_conf()`，「设置空闲事务超时」这个动作真执行时会在 reload 那一步失败，而评测从来没真正执行过它。另一个坑是函数的 EXECUTE 权限是按数据库授予的，脚本第一版授在了错误的库里。修完之后，全新安装跑 `check.sh` 注入全部 6 种故障，6/6 通过。

**4. 有技能不等于更快。** 最终批次的数据很诚实：有技能每次诊断慢约 6 秒、多约 9000 token，这是加载技能说明的代价；但工具步数从 12 步降到 7 步，准确率从 33% 升到 96%。我们在报告和路演里都照实讲，没有只挑好看的数字。

**5. 负向用例两边都满分。** 起初我们以为技能在安全上也会拉开差距，结果无技能基线的负向用例同样是 100%。这说明 Nemotron 本身就守规矩；而我们的安全护栏本来就放在服务端（只读角色、SQL 白名单、A/B/C 三档闸门、智能体自带的确认参数一律丢弃），不依赖模型自觉。

**6. 口令进了聊天记录就当泄露。** 调试时网站的访问 token 被贴进了聊天，我们立刻在节点上轮换，旧 token 返回 401。能改动系统的入口都要求 token（DGX 页面上的在线体验是只读的，由服务器代为鉴权），仓库里没有任何口令，公开仓库每次推送前都跑一遍审计脚本，推送后再从新克隆里独立复查一遍。

## 四、证明它有用

评测设计是整个项目最花心思的部分：同一模型、同一任务文本、同样的基础工具，唯一差别是是否加载技能。注入的会话用中性的应用名，模型读不出答案。23 道题（14 道正向、9 道负向），每题 3 轮，两种模式，共 138 次运行：

- PostgreSQL 根因准确率：33.3% → **95.8%**
- 工厂设备 + 故障类型都对：16.7% → **100%**
- 负向用例：两边都是 100%，危险尝试都是 0
- 证据可追溯率：92.5% → 96.5%

最能说明问题的是「长事务未提交」：持锁的会话处于 idle 状态，只看活动会话就会误判成锁竞争。无技能基线这一题 3 次都没答对，我们演示时看到的都是误判成锁竞争；有技能则直接找出持锁会话的 pid 和表。后来我们把故障实验室改成两种模式**同时**诊断同一个故障，页面上并排看，一分钟左右两边都出结论，差别一目了然。

## 五、收尾

最后两天做的都是「让别人能用、能信」的事：中英双语网页和演示视频、路演 PPT、公开仓库、网站换成 HTTPS、演示彩排（5 个步骤连跑 3 次，15/15 通过）。

回头看，这次比赛最大的收获不是某个功能，而是一个习惯：**先想清楚怎么证明，再动手做**。有了客观的标准答案和同条件对照，每一次改动好不好，都能用数字回答。

下一步，我们想把这套技能结构搬回金仓，再扩展到 MySQL 和 TiDB——换的只是取证脚本和故障库。让每个数据系统都有一个在本地、会自证的值班智能体。

—— 团队 GPTOPS
